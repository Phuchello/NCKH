# Architecture Decision Records (ADRs)

This document records the foundational architectural decisions for **Intel OS / NCKH Intelligence Platform**.

---

## ADR-0001: Cloud-First Authoritative Storage Architecture with Bounded Local Caching

* **Status**: Accepted
* **Date**: 2026-08-16
* **Context**: Research data and personal intelligence must persist across hardware upgrades, multi-device access, and potential laptop loss or corruption. Operating a local database as the primary system of record creates fragility and limits long-term value.
* **Decision**: 
  1. All authoritative structured data, intelligence graphs, and memory are stored in a cloud-hosted PostgreSQL database.
  2. Raw artifacts (PDFs, HTML snapshots, extracted figures) are stored in S3-compatible cloud object storage.
  3. The local laptop SSD is strictly used for source code, transient parser buffers, test fixtures, and a bounded cache governed by `MAX_LOCAL_CACHE_GB` (default 10 GB).
  4. External USB HDDs are treated as offline cold archives and secondary backup destinations, not live database hosts.
* **Consequences**:
  * *Positive*: High durability, seamless multi-device access, zero risk of data loss from laptop hardware failures.
  * *Negative*: Requires network connectivity for full platform synchronization, though cached data can be accessed locally.

## ADR-0002: Relational PostgreSQL + pgvector with V1 Versioned Embedding Contract (768 Dimensions)

* **Status**: Accepted
* **Date**: 2026-08-16
* **Context**: The platform requires both strict relational integrity and semantic vector search. Standalone vector databases introduce distributed transaction complexity and dual-write issues. Furthermore, pgvector requires a fixed column dimensionality.
* **Decision**: 
  1. Utilize PostgreSQL 16+ with the `pgvector` extension for relational data and vector embeddings.
  2. Establish a strict **V1 Versioned Embedding Contract of 768 dimensions** across vector columns (`document_chunks.embedding`, `claims.embedding`, `research_ideas.embedding`).
  3. Upgrading embedding dimensions in the future will be executed via versioned migration scripts and asynchronous table backfills rather than dynamic heterogeneous column sizing.
* **Consequences**:
  * *Positive*: Single ACID-compliant database, unified SQL queries joining relational filters with cosine distance (`<=>`), simplified backups, zero distributed synchronization overhead.
  * *Negative*: Dimensionality changes require schema migrations and re-indexing passes.

## ADR-0003: Multi-Tiered Retention Policy (Discovered → Indexed → Relevant → Retained → Archived)

* **Status**: Accepted
* **Date**: 2026-08-16
* **Context**: Ingesting thousands of research papers and articles can quickly consume terabytes of storage if every discovered document is downloaded and stored permanently.
* **Decision**: Implement a five-tier retention funnel:
  1. `DISCOVERED`: Metadata-only entry in PostgreSQL (`metadata_fingerprint`, title, DOI, authors, venue).
  2. `INDEXED`: Extracted abstract, normalized keywords, fast topic embedding.
  3. `RELEVANT`: Parsed clean text and structural markdown sections.
  4. `RETAINED`: Original raw artifact (PDF/HTML) uploaded to S3-compatible storage with versioned `document_snapshots` records.
  5. `ARCHIVED`: Cold storage snapshot for long-term project provenance.
* **Consequences**:
  * *Positive*: 90%+ storage cost savings, enables massive scale discovery without disk or bandwidth exhaustion.
  * *Negative*: Ingest pipeline must implement clear heuristic and classification stages to promote documents between tiers.

## ADR-0004: Explicit Snapshot-Pinned Relational Provenance over Opaque Vector-Only Lineage

* **Status**: Accepted
* **Date**: 2026-08-16
* **Context**: Research proposals and hypotheses generated by AI often suffer from hallucinations or unexplainable recommendations. Vector similarity alone cannot answer *why* an idea was synthesized. Furthermore, documents evolve over time (e.g. arXiv revisions).
* **Decision**: Enforce explicit relational provenance records (`Idea → Opportunity → Gap/Contradiction → Findings → Claims → Evidence → Snapshots → Documents → Sources`). Every claim must pin the exact `document_snapshots` version and quote offsets.
* **Consequences**:
  * *Positive*: 100% auditable scientific provenance, high trust, reproducible scientific rationale across document revisions.
  * *Negative*: Requires structured extraction pipelines that parse papers into atomic claims rather than storing only raw unparsed chunks.

## ADR-0005: Decoupled Replaceable LLM Reasoning Providers vs Versioned Embedding Contract

* **Status**: Accepted
* **Date**: 2026-08-16
* **Context**: Foundation models evolve rapidly. The system must decouple general reasoning engines from the underlying persistent vector index.
* **Decision**: 
  1. Model training is an explicit non-goal for G0 through V1.
  2. Implement an abstract reasoning LLM gateway supporting interchangeable providers (Gemini, Claude, GPT).
  3. Maintain a fixed V1 Embedding Contract (768-dim) for database vector search.
  4. The durable asset is the structured intelligence database, not the model weights.
* **Consequences**:
  * *Positive*: Instant upgrades as reasoning models improve, low operational costs, clean architectural boundaries.
  * *Negative*: External API latency must be managed via caching and asynchronous workers.

## ADR-0006: Modular Monolith Architecture (FastAPI Backend + Next.js Frontend) for V1

* **Status**: Accepted
* **Date**: 2026-08-16
* **Context**: Microservice architectures introduce high operational complexity, distributed latency, and networking overhead during the early phases of a platform.
* **Decision**: Adopt a modular monolith architecture:
  * Backend: Python FastAPI application with modular domain packages (`ingestion`, `parsing`, `reasoning`, `memory`, `opportunity`, `synthesis`, `workers`).
  * Frontend: Next.js 15+ application with clean REST API integration.
  * Storage: Shared PostgreSQL + S3 backend.
* **Consequences**:
  * *Positive*: Rapid development velocity, trivial local setup, straightforward end-to-end testing, clear module boundaries.
  * *Negative*: Requires disciplined code modularity to prevent tight coupling between domains.

## ADR-0007: Defense-in-Depth Security Model for Ingestion (SSRF, Prompt Injection, Malicious Content)

* **Status**: Accepted
* **Date**: 2026-08-16
* **Context**: Crawling arbitrary web URLs and parsing untrusted academic PDFs introduces security vectors including SSRF, prompt injection embedded in document text, and PDF parser exploits.
* **Decision**:
  1. SSRF Guard: Validate all URLs pre-flight, resolving DNS and blocking private/loopback IP ranges (RFC 1918, RFC 4193, 169.254.169.254) before opening connections.
  2. Prompt Injection Mitigation: Treat all parsed document text as untrusted data. Use strict XML sandboxing delimiters and structured JSON schema outputs with no direct script evaluation.
  3. Content Isolation: Limit PDF file sizes (50 MB limit) and enforce timeouts on parsing routines.
* **Consequences**:
  * *Positive*: Layered security perimeter reducing vulnerabilities across infrastructure.
  * *Negative*: Slight processing overhead on pre-flight DNS validation.

## ADR-0008: Dual AI Agent Development Policy (Gemini/Antigravity Scaffolding vs Codex Surgical Intervention)

* **Status**: Accepted
* **Date**: 2026-08-16
* **Context**: Development efficiency requires matching the right AI tool to the appropriate engineering challenge to optimize speed, context window, and reasoning budget.
* **Decision**:
  * **Gemini / Antigravity**: Primary agent for end-to-end feature development, research exploration, comprehensive documentation, API endpoints, frontend UI, prompt engineering, and test suites.
  * **Codex**: Reserved strictly for high-concurrency bugs, idempotency verification, transaction isolation audits, complex migrations, security-critical implementations, and final engineering audits.
* **Consequences**:
  * *Positive*: Maximizes development velocity while preserving high-tier reasoning for complex architectural bottlenecks.

## ADR-0009: Many-to-Many Topic Cardinality & Multi-Provider Document Reconciliation

* **Status**: Accepted
* **Date**: 2026-08-16
* **Context**: Scientific papers naturally span multiple topics (e.g. Edge AI, Sparse Sensing, Digital Twins). Additionally, the same paper may be observed across multiple providers (arXiv, Crossref, Semantic Scholar).
* **Decision**:
  1. Replace 1:N topic ownership with a Many-to-Many junction table (`document_topics`).
  2. Make `sources` global and reusable.
  3. Introduce `document_sources` to record multi-provider observations while reconciling them into a single canonical `documents` record.
* **Consequences**:
  * *Positive*: Flexible multi-domain research modeling, zero duplication of papers observed across multiple sources.
  * *Negative*: Queries require explicit junction joins.

## ADR-0010: Orthogonal Scientific Epistemology Framework (Grounding vs Epistemic Status vs Evidence Quality)

* **Status**: Accepted
* **Date**: 2026-08-16
* **Context**: Conflating verbatim textual presence with scientific truth produces invalid knowledge graphs. A paper may state a hypothesis or a flawed claim verbatim.
* **Decision**: Decouple scientific extraction into four orthogonal dimensions:
  1. `grounding_status`: Verifies textual presence (`VERBATIM_MATCH`, `PARAPHRASE_VERIFIED`, `UNVERIFIED`, `FAILED`).
  2. `claim_type`: Identifies statement nature (`EMPIRICAL_FINDING`, `AUTHOR_HYPOTHESIS`, `LIMITATION`, `FUTURE_WORK`, etc.).
  3. `epistemic_status`: Represents validated truth status (`UNASSESSED`, `SUPPORTED`, `CONTESTED`, `REFUTED`, `CONSENSUS`, `SPECULATIVE`), defaulting to `UNASSESSED`.
  4. `evidence_items`: Stores empirical benchmark data, sample sizes, and p-values.
* **Consequences**:
  * *Positive*: Scientifically rigorous knowledge representation; prevents unverified assertions from masquerading as supported scientific facts.
  * *Negative*: Requires secondary validation passes to promote claims from `UNASSESSED` to `SUPPORTED`.
